## Fix P7 — seam doctrine (RED phase + blueprint + reviewer prompt)

Three edit points. All additions are doctrine or reviewer-prompt dimensions — advisory, never a new gate (rule 4). The deterministic piece (name-set gate) already exists.

### P7-a `feature-dev.md` Phase 4 (RED), insert as the phase's first step (before "Role:")

> 1. **Test only at the AC's seam, read from the blueprint.** The seam is the substitution point: where behavior can change without editing the code (Feathers: "a place where you can alter behavior in your program without editing in that place", wiki `test-seam` §定义与机制). The test observes the AC's public boundary THROUGH the seam. The boundary is the public interface the caller actually uses (public fn / endpoint / UI event), never an internal helper (wiki `test-seam` §为什么在接缝处测试). Read the seam from the blueprint's AC line (frozen at Phase 0; the RED phase consumes it, it does not renegotiate it); only if the AC line carries no seam, identify one here and note the degrade (P7-b). Feathers enumerates three seam types (wiki `test-seam` §定义与机制, verified):
>
>    | Seam type | Mechanism | Examples |
>    | --- | --- | --- |
>    | object seam | interface/DI substitution | Rust traits, Java interfaces, Python protocols |
>    | link seam | module/link-time substitution | linker substitution |
>    | preprocessing seam | build-time substitution | conditional compilation |
>
>    (The type names + mechanisms are the wiki's; the Examples column is this proposal's own instantiation.)
>    The doctrine picks by language among object and link seams ONLY — preprocessing seams are scoped out (build configuration, not behavior under test); a language whose only seam mechanism is conditional-compilation-style preprocessing is outside this doctrine's coverage, stated honestly. The scoping-out is this proposal's own judgment, not a wiki claim. Each seam has an enabling point — the seam says where behavior can change, the enabling point says who decides which variant is used (wiki `test-seam` §定义与机制). The test sets the enabling point to inject the variant under test.
> 2. Do not write: implementation-coupled tests (renaming an internal fn breaks the test with no behavior change; mocking own modules' internals; asserting call counts; using db queries to verify instead of the interface); tautological assertions (expected value computed the same way as the code — the expected value must come from an independent truth source: a known-good literal, a hand-worked example, the spec). (wiki `test-seam` §AI 编码中的接缝纪律 · 三种测试反模式; mattpocock's own `docs/engineering/tdd.md:81-84` lists the good-test mirror of the same concerns as positive criteria — test names read as capabilities, expected values traceable to the spec, internal rename breaks nothing, mocks only at external boundaries.) The third wiki anti-pattern — test-batch horizontal slicing (all tests first, then all code) — is solidforge's DELIBERATE Phase-4 exception: the RED batch is the parallel-contract design (tests = the shared API contracts parallel implementers converge against, feature-dev.md:72). Rejected with rationale, recorded in the ADR entry — not imported, not silent (rule 3).

Same one-sentence cross-ref added to `SKILL.md` TDD Default and `bug-fix.md` RED (rule-5 doc-audit, enumerated below).

### P7-b `intent-blueprint.md` AC definition + `infra/templates/intent-blueprint.template.md` gain the seam field

Each AC line declares its seam at Phase 0 freeze: `AC-1 <Given/When/Then> — seam: <public-boundary-name>`. The declaration carries a one-clause catch/miss note (what this boundary catches, what it misses — wiki `test-seam` §权衡与局限 · 接缝选择摩擦: a bare name is label-blind-picking; the catch/miss clause is the mitigation). The canonical AC-line carrier — `infra/templates/intent-blueprint.template.md` (template line 23, referenced by intent-blueprint.md:7) — gains the same `— seam:` tail, else newly authored blueprints default to the absent-seam degrade. The `AC → test mapping` line format stays UNCHANGED (the seam lives on the AC line, not the mapping line, so `parse_ac_test_map` — the regex-matched gate parser — is untouched; rule 2, never edit the checker). Absent seam on the AC line → **no gate consequence** (advisory doctrine; the name-set gate is unaffected — it reads the mapping section only) — RED identifies the seam mid-phase per P7-a; NO schema'd record carrier exists for that identification. The run-record schema has no notes field and `additionalProperties: false`; `loop_state.py summary()` is a deterministic f-string with no free-text input; the folded inner summary is produced by the GREEN-phase Coder, not the RED-phase tester. `record-outer --notes` exists but is an outer-review anchor that bumps `outer.iterations`; calling it at RED would corrupt the DoD accounting, so it is explicitly excluded. The degrade is therefore unverifiable at the producer end, stated honestly. The consumer end closes the loop via reviewer check (g): tests sit at a public boundary, and the absent declaration is flagged as its own finding — at warning severity, consistent with the prompt template's item-3 severity line. Warning-severity findings never block by workspace rule 4 (advisory, never Blocker — a Blocker must be a real violation); that rule is the non-conflict source, and the implementation makes the interaction explicit in the template's verdict line (warning-only findings do not change a pass verdict). The identification is NEVER written into the frozen blueprint (blueprint_guard.py denies edits to a `status: frozen` blueprint). Deliberate design consequence: the seam field is declared PRE-freeze at Phase 0 precisely to avoid the AC→test mapping's unreconciled post-freeze write path — the mapping is declared at RED (post-freeze) yet blueprint_guard.py wholesale-denies frozen blueprints; how the mapping section enters the frozen blueprint is a pre-existing repo question, recorded here as an implementation-time open question, not this proposal's to solve. A systematic absent seam is a defect, not the norm — see the rich-path rule below.

**Rich path**: when the blueprint is derived from a bc spec (`plan_queue.detect_producer` reports `blueprint-crafting`), bc carries no seam field (bc is out of scope here) — the pd Planner derives the seam AT Phase-0 derivation from the AC's Given/When/Then boundary (the external call boundary the scenario names) and writes it into the derived blueprint. Derive, don't re-imagine — the anchor stays upstream and real; the degrade stays the exception, not the rich-path norm. Refactoring runs freeze blueprints whose ACs are the existing behavior-locking tests (refactoring.md Phase 0 — the acceptance criteria = the existing tests, which Phase 2 produces; if tests are missing at freeze, Phase 2 writes them first). The seam derives from the locked tests' observed boundary (the tests themselves are the seam evidence); refactoring Phase 0 writes the derived seam onto the AC lines at freeze. When the locking tests do not yet exist at freeze, the seam is declared from the boundary the Phase-2 tests will lock. The declaration is present at freeze, so check (g)'s conformance path applies and no systematic absent-seam noise is produced.

This is mattpocock's "pre-agreed seam" translated to solidforge idiom: the seam is agreed at blueprint freeze (upstream), the RED phase consumes it — not a mid-RED chat confirmation. The wiki's upstream-anchoring point applies: a guard whose precondition is never anchored upstream silently degrades to "just write code" (wiki `test-seam` §AI 编码中的接缝纪律 · 上游冻结).

### P7-c `convergent-loop.md` — BOTH test-quality enumerations (flow line 67 + the operative "Reviewer subagent prompt template" item 3)

The doc carries the test-quality checklist twice: the flow description (line 67) and the operative prompt template the reviewer subagent actually receives (§ "Reviewer subagent prompt template", lines 187-206 — its item 3 enumerates (a) happy-path-only gaps, (b) weakened assertions, (c) deleted/renamed mapped tests). Editing only line 67 would leave the new checks out of the reviewer's prompt — the rule-8 reachability failure at the review decision point. Amend BOTH:

- **Template item 3 gains four checks**: (d) tautological assertion — is the expected value computed independently of the implementation (known-good literal / hand-worked example / spec), or derived the same way the code derives it; (e) implementation-coupled test — does the test break on an internal rename with no behavior change; does it mock own-module internals, assert call counts, or use db queries to verify instead of the interface; (f) no independent truth source — if the change has no assertable independent truth source, seam tests degenerate to tautology from the other direction; flag it as a finding of its own (wiki `test-seam` §权衡与局限 · 根缺口 — the wiki ties this gap's RESOLUTION to the 异源-oracle result-axis constraint, isomorphic to two-axis-evaluation-separation; this check is the same-family tripwire only, not the resolution); (g) seam conformance — do the tests sit at the seam declared on the blueprint AC line; testing a different boundary than the frozen one is a finding. No seam declared on the AC line (the legal absent-seam degrade) → check the tests sit at a public boundary and flag the absent declaration as its own finding. (mattpocock's code-review half of the pre-agreed-seam mechanism: "/code-review checks that only agreed-upon test seams were used".)
- **Flow line 67** gains the same four checks in its one-line summary, cross-referencing the template.
- Same-family ceiling note unchanged (ADR #38) — (d)(e)(f)(g) are all same-family checks.

## Fix P8 — tracer-bullet-first decomposition (plan interpretation + refactoring)

### P8-a `plan-driven-mode.md` Phase −1, add a decomposition doctrine (extends the sequence-intent extraction)

- **Tracer-bullet first**: for end-to-end feature plans, the first wave (`parallel_group` wave-1) is a thin vertical slice through ALL layers (minimal path through schema/API/UI/tests — the upload→parse→store→display minimum). Later items extend on that skeleton. A tracer bullet is keepable production code, not a throwaway prototype (Hunt & Thomas). Rationale: horizontal slicing delays feedback to the last layer, breeds abstractions no later layer uses, and defers integration testing (wiki `tracer-bullet` §竖切与横切的对照). **Wave-1 composition**: wave-1 is the single tracer-bullet item, or items that jointly form one thin slice; nothing else rides wave-1 (an unrelated item placed beside the slice runs concurrently with, not extends on, the skeleton — the per-item shape rules govern item shape, not wave composition).
- **Per-item shape rules** (applied at normalization, surfaced at the checkpoint):
  - Each item is demoable/verifiable on its own — its AC subset observable without later items. Validation question: "what can be demoed when this item completes?" No answer → it is a horizontal slice, split it (wiki `tracer-bullet` §权衡).
  - Each item fits ONE Coder fresh context — the Coder is a fresh subagent per item (`convergent-loop.md:14`), so the item-size bound maps directly to the executor's context capacity.
  - An item's AC subset does not reach into other items' territory.
- **Skip slicing** when the whole change fits one context window — slicing is pure overhead then.
- **Wide-refactor exception**: a mechanical change whose blast radius spans the codebase cannot be vertically sliced (no slice independently greens) — decompose as expand-contract instead (P8-b).
- **Precedence over latched decompositions**: Phase −1's extraction doctrine latches upstream structure (iteration-plan tables, Cursor `todos[]` — plan-driven-mode.md §Phase −1, "Latch (structural — high confidence)") and keeps plan-native grain. The tracer-bullet shape rules bind the semantically-inferred decompositions; on LATCHED decompositions they are checkpoint-flagged advisory findings (revision channel), never a silent re-split of latched grain.
- **Default-mode reachability (rule 8)**: feature-dev.md Phase 1 "Break down into subtasks" is the default (non-plan-driven) decomposition decision point — it gains a one-sentence cross-ref to this doctrine so the thin-slice-first rule is reachable where default-mode decomposition happens.
- Honest limit: this is normalization doctrine (L3 semantic, checkpoint-surfaced), NOT a gate (rule 4).

### P8-b `refactoring.md` Phase 3, add the expand-contract carve-out

For wide mechanical refactors (rename a column, change a shared symbol type — blast radius across the codebase):

- **Expand**: new form coexists with the old; nothing breaks.
- **Migrate**: batch call-site migration by package/dir, each batch one unit, all blocked by expand; CI stays green because the old form still exists.
- **Contract**: delete the old form after no callers remain; blocked by all migrate batches.

The blocking semantics need a carrier: `refactoring.md` Phase 3 is a prose workflow with no dependency machinery. A wide refactor decomposes ONLY via plan-driven mode (the plan queue's `depends_on` carries the expand→migrate→contract blocking edges); `refactoring.md` Phase 3 gains a routing pointer — "wide mechanical refactor (blast radius across the codebase) → plan-driven mode with an expand-contract queue; a plain Phase-3 run cannot sequence the batches". Entry path, binary: with a plan @ref (a bc-authored expand-contract iteration plan, or a user-provided one), plan-driven mode carries the CI-green guarantee; for a plain conversational wide-refactor request with no plan, the expand-contract sequence is a Phase-3 advisory note (batches run unsequenced, the CI-green guarantee is LOST — honest coverage note) and the orchestrator surfaces the plan option to the user (bc authoring the plan, then pd executing it) rather than silently choosing — the orchestrator does NOT self-author the plan (plan authoring is out of pd's scope per the Scope Guard).

Horizontal slicing is legal WITHIN the blast radius (one batch per package); it stays illegal ACROSS layers. Expand-contract is the seam idea serialized: the new form introduced at expand IS the new seam, migration proceeds along it (wiki `tracer-bullet` §宽重构例外).

## P9 — review-axis separation, recorded as ODP, NOT implemented

mattpocock's code-review splits the semantic review into two parallel sub-agents (standards axis / spec axis), reports separately, never merges, one worst-issue per axis — so a passing axis cannot mask a failing one. solidforge's single-agent triple-line review has the same masking risk in principle. But two existing mechanisms cover part of the benefit: the codable share of standards (lint/fmt/arch contracts) lives in the inner ring; the axis's judgmental residue — repo-doc conventions + annotated smells, which the wiki defines as the standards axis's actual subject (linter-enforced content is skipped by BOTH axes, wiki `review-axis-separation` §标准轴的来源层级) — stays in the single-agent semantic line, i.e. part of the residual masking risk the ODP trigger watches; and blind-spot crossing is the 异源 leg's job (`convergent-loop.md:78-104` — note the cited section scopes it as OPT-IN: high-stakes items only, human-judged trigger; default items do NOT run it); no cross-family mechanism appears in the vendored mattpocock materials or the wiki summaries (mattpocock's code-review.md is not vendored — the negative is bounded to the vendored record, stated honestly). The deferral therefore covers default items imperfectly — see the ODP trigger below. Known cost of the split: per-axis sub-agents can re-discover the review command and recursively fan out (observed to tens of agents — wiki `review-axis-separation` §轴独立性如何实现), so a split would need an explicit no-delegation rule.

Record as an Open Decision Point: trigger for re-evaluation = an observed masking incident (a converged item whose one axis failed while the verdict passed) — explicitly including a masking incident on a DEFAULT item (no 异源 leg ran), where the blind-spot-crossing backstop was absent. Incident feed, named: 异源-leg disagreements on high-stakes items the same-family verdict passed, and human post-mortems (the merged verdict emits no per-axis signal, so the current record cannot self-observe a masked failure — stated honestly). Carrier: the ADR entry below (design-decisions.md carries no ODP machinery — that is plan-queue-level; the entry re-surfaces whenever a future test-quality or review-structure change consults design-decisions.md — no automated re-surface point, stated honestly). Not in plan queues — it is a skill-level ODP, not a plan-level one.

## Validation notes (reverse-direction evidence)

Two findings from the wiki research validate existing solidforge architecture rather than adding gaps:

- mattpocock dropped the refactor phase from its TDD loop in June 2026 — its own doc states "it was dropped in June 2026 because agents essentially never performed it, and because review and implementation work better as separate sessions" (mattpocock `docs/engineering/tdd.md:31`, fetched + verified 2026-08-24 — NOT the wiki page; the wiki summary omits this finding). Refactoring moved to code-review. solidforge's own refactor placement is mixed: the TDD Default nominally lists REFACTOR as step 3 of the per-task cycle (SKILL.md:13-15), while operationally refactoring runs as an optional phase AFTER convergence (feature-dev.md Phase 7 tail) and the convergence loop itself carries no refactor step (convergent-loop.md: 0 REFACTOR occurrences, verified). Mattpocock's change validates the OPERATIONAL half of that split (refactor after review, separate from the test cycle) and exposes the internal tension between the nominal step 3 and the operational post-convergence phase. Record both in the ADR entry — including the open question: demote step 3 in the TDD Default text to match the operational shape?
- mattpocock's implement does not close work units — closing is left to the human (wiki `mattpocock-skills` §诚实的失效模式文档: "实现不关闭工作单元（关闭由人负责）"), so the machine-observable work-unit CLOSURE state never advances from the implement step. The implement run itself lands code (beat 5 commits to the branch, vendored excerpt) — landed artifacts ARE a frontier delta per the invariant's 机制 definition (已落盘的可执行产物); the contrast with solidforge's `plan_queue.py complete` is the machine-observable closure/status delta, not artifact landing (wiki `frontier-delta-progress-invariant` §机制 + §在失效谱系中的位置, vendored at the csr workspace; record in the ADR entry).
